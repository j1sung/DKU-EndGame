# AI 작업 및 프로젝트 문서 관리 체계 — 최종 설계

> 최종 갱신일: 2026-10-01 (KST)
> 상태: 지침·스킬 및 문서 재배치 적용 완료 · 초기 대표 문서 작성 · 에디터 내부 확인과 GitHub ID 확인은 보완 필요

## 1. 목적과 문서의 위치

AI가 작성한 코드뿐 아니라 팀 전체의 구현을 카테고리별로 파악하고, 변경 배경과 작업자를 추적하기 위한 최소 관리 체계.

- 대표 문서만 읽어도 해당 분야의 현재 구조 파악 가능.
- 기능별 최근 변경 날짜·작업자 표시.
- 짧은 변경 이력에서 대표·상세 문서로 바로 접근.
- 승인된 AI 구현 작업에서는 관련 문서를 함께 갱신.
- 사람이 직접 수행한 작업과 누락된 기록은 문서 갱신 스킬로 정리.
- 당장은 Hive·OMX·검색 DB·여러 에이전트 운영 체계 미도입.

이 문서는 사람이 구성과 설계 이유를 이해하기 위한 참고 자료. AI가 매 작업에서 읽는 필수 지침에 포함하지 않으며, 체계 자체의 수정·검토를 요청받았을 때 참고 가능.

실제 행동 규칙은 `AGENTS.md`와 `.agents/directives/`, 수행 절차는 스킬이 담당. 적용 후 이 설계 문서와 실제 규칙이 달라지면 관련 문서를 함께 정리하고, 충돌하는 설명을 방치하지 않기.

## 3. 역할과 언어

| 구성 | 역할 | 언어 |
|---|---|---|
| `AGENTS.md` | 핵심 제한과 지침 선택 기준을 제공하는 입구 | 영어 |
| `.agents/directives/` | AI의 판단·조사·개발·기록·협업 규칙 | 영어 |
| `SKILL.md` | 초기 문서화와 기존 문서 갱신 절차 | 영어 |
| `templates/` | 대표·상세 문서와 변경 기록 양식 | 한국어 |
| `prompts/` | 사람이 선택해서 사용하는 작업 요청문 | 한국어 |
| `Docs/` | 사람과 AI가 함께 참고하는 프로젝트 지식 | 한국어 |

코드 심볼·에셋 이름·경로·명령은 원래 표기 유지. 프로젝트 설명을 AI용 영어 문서로 중복 작성하지 않기.

## 4. 지침별 책임

### AGENTS.md

- 프로젝트 기본 정보와 확인된 엔진 버전.
- 명시적 요청 없이 구현·반영하지 않는 핵심 제한.
- 언어 구분과 작업별 지침 선택표.
- 관련 Docs 탐색 위치와 문서화 스킬 사용 조건.
- 세부 지침의 폴더 존재만으로 자동 적용을 가정하지 않고 읽기 조건 명시.

### 01-behavior-and-evidence.md

- Unreal C++ 협업자·멘토 역할. 작은 팀이 이해하고 유지할 수 있는 단순한 구현 우선.
- 한국어 설명, 필요한 Unreal 개념은 쉽게 설명.
- 질문·조사·구현 요청 구분 및 승인 범위 준수.
- 확인된 사실·가설·미확인 내용 구분. 추측을 사실처럼 표현하지 않기.
- 중요한 구조·규칙·원인 설명에 확인한 경로와 위치 제시.
- 파일명·검색 일부·잘린 출력만 보고 결론 내리지 않기.
- 관련 없는 코드·문서·에셋을 임의로 수정하지 않기.

### 02-context-and-token-policy.md

- 목차·키워드 검색 → 관련 대표 문서 → 필요한 상세 문서·Git 이력 → 코드·에셋 순서로 조사.
- 현재 작업에 필요한 지침·스킬·파일만 로딩.
- 동일 대화에서 확인한 내용은 변경 근거가 없으면 반복해서 읽지 않기.
- 구현 수정에서는 대상 코드와 필요한 호출·의존 관계 확인.
- 문서 누락·오류·구현 불일치가 있으면 조사 범위 확대.
- 토큰 절약을 이유로 필요한 확인을 생략하지 않기.
- 찾은 후보가 모호하거나 대상이 없으면 검색 범위를 밝히고 경로·이름 확인 요청.

### 03-unreal-development.md

- 관련 Unreal 공식 문서를 기본 기준으로 삼고, 실제 프로젝트의 기존 구현·명명·폴더·포맷 관례 존중.
- 새 코드와 에셋은 공식 기준 및 프로젝트 관례를 확인해 일관되게 작성.
- 지침 도입을 이유로 기존 코드 일괄 정리나 에셋 이름·경로 변경 금지.
- 공식 권장 방식과 기존 관례가 충돌하면 차이와 영향을 설명. 중요한 선택은 작업자에게 확인.
- 공식 기준이 없는 관례는 프로젝트 규칙 또는 제안으로 구분.
- Unreal 명명, 리플렉션, 객체 수명·참조, 서버 권한·RPC·복제 여부 고려.
- 주석은 코드 반복보다 구현 의도·제약·주의점 설명에 집중.
- 불필요한 추상화와 요청하지 않은 기능·프레임워크 도입 금지.
- 실제 연결된 MCP의 상태·도구·입력 형식과 대상 프로젝트·에셋 확인.
- 조사에서는 읽기 작업만 수행. 변경은 승인 범위에서 진행하고 변경 후 상태 재확인.
- 도구 호출 성공을 실제 게임 동작 검증으로 표현하지 않기.
- 빌드·컴파일·PIE·저장 등은 승인된 실행·변경 범위인지 확인.

### 04-documentation.md

- 대표 문서는 날짜별 일지가 아니라 현재 구현의 설명으로 유지.
- 기존 양식·목차를 가능한 한 보존하면서 변경된 내용을 제자리에서 갱신.
- 유효한 설계 이유·주의사항을 줄이거나 이동할 때 상세 문서로 보존하고 링크 유지.
- 잘못되거나 대체된 설명은 수정. 과거 상태는 Git으로 추적.
- 상세 문서는 긴 기술 설명이 필요할 때만 생성.
- 기능별 작업자·날짜, 전체 갱신 기준, Changes 중복 방지, 목차·링크 관리.
- 질문·조사만으로 문서 생성 또는 변경 이력 작성 금지.

### 05-git-and-team-workflow.md

- `main`: 버전업할 때만 `dev`를 병합.
- `dev`: 팀 작업을 모으는 통합 브랜치.
- 개인 작업 브랜치: `dev`에서 각자 이름으로 생성하여 작업.
- 개인 작업은 `dev`에 자주 병합.
- 다른 사람의 작업을 수정하거나 작업 전달·후속 작업이 필요한 변경은 `dev` 병합용 PR을 올리고 Discord에 별도 코멘트로 공유.
- 기존 작업 및 다른 작업자의 변경 보존. 문서 이동 시 충돌과 링크 손상 확인.
- 이 전략을 인지하는 것과 실행 권한은 구분. 커밋·푸시·병합·PR 생성·Discord 전송은 명시적으로 요청한 범위에서 수행.

## 5. 승인 범위

| 요청 | 허용 범위 |
|---|---|
| 설명·비교·설계 논의 | 답변과 읽기 전용 조사 |
| 프로젝트 확인 | 관련 파일·상태 조사 |
| 파일 생성·수정·구현·적용 | 명시한 범위의 변경 |
| 빌드·실행·설치 | 명시한 실행 작업 |
| 커밋·푸시·병합·PR·메시지 전송·삭제 | 명시한 해당 행동 |

논의 중의 동의 표현을 구현 승인으로 확대 해석하지 않기. 승인된 구현에서는 관련 문서 갱신까지 처리하되 매 파일마다 재승인을 요청하지 않기. 질문·조사에서 문서 오류를 발견하면 우선 알리고 수정 요청 전에는 반영하지 않기.

## 6. Docs의 역할

### index.md

카테고리 대표 문서, 필요한 상세 문서, Changes 및 이 운영 설계로 연결하는 탐색 목차.

### 카테고리 Overview.md

해당 파일만 읽어도 현재 카테고리 구조 파악이 가능한 대표 문서.

- 담당 범위와 주요 기능.
- 동작 흐름과 연결 관계.
- 관련 코드·에셋.
- 확인된 설계 이유·제약·미구현 범위.
- 필요한 상세 문서 링크.

### 상세 문서

복잡한 흐름·기술 설정·설계 배경을 설명할 필요가 있을 때 같은 카테고리 안에 작성. 대표 문서와 상호 연결. 동일 주제는 기존 문서 갱신 우선.

### Changes.md

한 파일에 최신 변경부터 짧게 기록. 기록에서 대표 문서의 해당 절과 필요한 상세 문서로 바로 접근.

## 7. 두 가지 갱신 경로

### 승인된 AI 구현 작업

관련 문서·구현 확인 → 구현 및 승인된 검증 → 대표·상세 문서 갱신 → 기능별 날짜·작업자 갱신 → Changes 기록 → 필요한 목차·링크 수정.

이 경로에서는 대표 문서 상단의 전체 갱신 날짜와 기준을 변경하지 않기.

### 사용자가 요청한 전체 문서 갱신 스킬

1. 기존 문서와 마지막 전체 갱신 기준 확인.
2. 기준 이후 Git 변경 및 커밋되지 않은 로컬 변경 확인.
3. 영향받은 카테고리의 현재 코드·에셋과 문서 대조.
4. 추가·수정·삭제된 구현에 맞춰 설명 갱신.
5. 의미 있는 기능 변경의 날짜·작성자를 Git 이력에서 확인.
6. 누락된 Changes 기록 추가 및 중복 방지.
7. 목차·링크 확인.
8. 확인을 완료한 대표 문서의 전체 갱신 정보 수정.

문서가 처음부터 없으면 관련 분야를 충분히 조사하여 작성. 기존 문서가 있으면 변경 내역으로 조사 범위를 좁히되, 누락·불일치가 발견되면 확대.

### 갱신 기준의 의미

갱신 기준 커밋은 조사 범위를 좁히는 출발점. 해당 기준 이후의 변경을 찾아 관련 문서를 현재 구현과 대조하며, 이력만으로 문서의 정확성을 판단하지 않기.

- 기준이 없거나 유효하지 않으면 관련 구현을 더 넓게 조사.
- 기존 문서의 오류·누락이 발견되면 기준 이전 구현도 확인 가능.
- 일부 확인 실패를 전체 갱신 완료로 표시하지 않기.
- HEAD 기준 커밋에 포함되지 않은 로컬 변경은 구분하여 취급. 그 상태까지 커밋으로 추적 가능한 것처럼 표시하지 않기.

## 8. 대표·상세 문서 양식

### 대표 문서 상단

```markdown
# Network 개요

> 전체 문서 갱신: 2026-10-01 · @문서갱신요청자
> 갱신 기준: 커밋 abc1234
```

해당 카테고리 전체 확인을 완료한 스킬 실행에서만 갱신. 날짜는 KST 기준. 갱신 요청자와 실제 기능 작업자는 별개.

### 기능별 표시

```markdown
## 방 종료

> 최근 기능 변경: 2026-09-30 · @기능작업자

현재 구현된 동작 설명…

- 관련 구현: `CFSessionSubsystem`, `CFWaitingNetwork`
- 상세 설명: [방 종료 처리](RoomClosing.md)
```

최근 동작·구조·설계 변경을 표시. 단순 이름·경로 변경만으로 기능 변경 정보를 덮어쓰지 않기. 본문의 이름은 최신화하고 해당 변경은 Changes에서 추적.

상세 문서도 기능별 변경 정보와 관련 개요 링크 사용. 구현 확인·실행 검증은 필수 기록 항목에서 제외하되 미확인 내용이나 실행하지 않은 결과를 단정하지 않기.

## 9. Changes 양식과 기록 기준

```markdown
<a id="change-20260930-01"></a>
### 2026-09-30 · 방장 퇴장 처리 변경

- 작업자: @기능작업자
- 배경: 방장 퇴장 후 참가자가 대기방에 남는 문제
- 변경: 방 종료 알림 후 참가자가 메인 메뉴로 돌아가도록 처리
- 문서: [Network 개요](Network/Overview.md#방-종료)
  · [방 종료 상세](Network/RoomClosing.md)
```

- 날짜별 파일·폴더를 만들지 않고 한 파일에 최신순 기록.
- 기능 및 의미 있는 이름·경로·설정 변경 기록.
- 의미가 같은 오탈자·서식 수정은 보통 생략.
- 상세 문서가 없으면 대표 문서 링크만 사용.
- 뒤늦게 발견한 작업은 원래 변경 날짜 사용. 중복 기록 금지.
- 확인된 커밋 링크는 필요할 때 추가. 기록을 위해 자동 커밋하지 않기.
- 개요·상세 문서에서 Changes로의 역링크는 필수 아님. 특정 변경 배경을 찾아볼 필요가 있을 때만 연결.

## 10. 작업자 추적

- 기능 작업자는 최근 의미 있는 변경의 실제 커밋 작성자를 기준으로 확인.
- 푸시 담당자·병합 담당자를 기능 작성자로 자동 지정하지 않기.
- Git 작성자 이름·이메일만으로 GitHub ID 추측 금지. 확인된 매핑 또는 GitHub 정보 사용.
- 확인이 어려우면 `작성자 확인 필요` 표시. 공동 작업은 복수 작업자 가능.
- 미커밋 작업은 확인된 작업자 정보가 있을 때만 기록하고 커밋 기반 추적과 구분.
- 기존 기능의 과거 작업자를 이번 문서 정리 요청자로 덮어쓰지 않기.

## 12. 스킬·템플릿·프롬프트

| 구성 | 책임 |
|---|---|
| 지침 | 판단 기준 |
| 스킬 | 수행 절차 |
| 템플릿 | 결과 문서 양식 |
| 프롬프트 | 사용자의 작업 요청 |

project-docs 스킬 하나가 초기 문서화와 기존 문서 갱신 담당. 템플릿은 새 문서 및 필수 항목 확인에 사용하며 기존 문서를 기계적으로 덮어쓰지 않기.

프롬프트 예시:

```text
project-docs 스킬을 사용해 프로젝트 문서를 전체 갱신해줘.

대상: 전체 카테고리
문서 갱신 요청자 GitHub ID: @아이디

현재 구현과 기존 문서를 대조하고 누락된 변경을 반영해줘.
기능별 변경 날짜·작업자는 관련 Git 이력으로 확인해줘.
코드·에셋은 수정하지 말고 문서만 갱신해줘.
커밋·푸시·빌드·실행은 하지 마.
```

프롬프트 폴더는 사람이 선택하여 사용하는 요청문 모음. 자동 실행 대상이 아니며 세부 규칙을 중복하지 않고 지침·스킬 참조.

## 15. 스테이징 커밋 스킬

`commit-staged`는 실행 요청 시 현재 변경을 검토하고 스테이징한 뒤 큰 작업 단위로 묶어 커밋하는 스킬. 메시지 초안만 요청하면 스테이징·커밋하지 않음.

- 같은 기능·수정과 관련 코드·에셋·설정·테스트·문서를 함께 묶기.
- 독립적인 큰 작업은 분리하고 자잘한 변경은 가장 관련 있는 묶음에 포함.
- 파일마다 나누거나 고정 개수로 세분화하지 않기.
- 제목: `feat: 캐릭터 기울기 구현`처럼 영어 태그와 한국어 요약.
- 본문: `-` 목록으로 간략한 변경과 이유 설명. 필요한 경우에만 ✅·⚠️ 사용.
- 기본 모드는 수정·삭제·새 프로젝트 파일을 검토 후 스테이징. 부분 스테이징 파일도 최종 작업 파일 기준으로 포함하며 사전 요약에서 알림. 명시적으로 스테이징된 것만 요청하면 기존 부분 스테이징 유지. 생성물·비밀정보·범위 밖 변경은 제외하고 이유 보고.
- 커밋 분할은 검토 후 스테이징된 스냅샷의 정확한 내용을 보존할 수 있을 때만 수행. 안전한 분리가 불가능하면 사용자에게 선택 요청.
- 푸시·병합·빌드·실행은 별도 요청. 스킬 생성은 현재 변경의 커밋 승인이 아님.
- 사용 예: `commit-staged 스킬로 지금 변경된 작업을 스테이징하고 큰 작업 단위로 묶어서 커밋해줘.`
