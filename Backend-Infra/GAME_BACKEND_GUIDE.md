# 4인 닭싸움 게임 백엔드·인프라 공통 가이드

## 1. 문서 목적

이 문서는 백엔드·인프라 작업 전반에서 유지할 공통 목표, 범위, 확정 결정, 작업 원칙을 정리한다.

- 스프린트별 세부 작업은 이 문서에 누적하지 않는다.
- 스프린트를 시작할 때 별도 체크리스트를 만들고, 완료 조건과 검증 결과를 함께 기록한다.
- 설계가 변경되면 변경 이유와 영향 범위를 먼저 기록한 뒤 이 문서의 관련 항목을 갱신한다.
- 문서에 나온 테이블, API, 상태 이름은 상세 설계를 거쳐 확정한다.

## 2. 프로젝트 목표

Unreal Engine 기반 캐주얼 닭싸움 게임에서 서로 다른 사용자 4명이 별도의 방 검색이나 코드 입력 없이 자동으로 매칭되어 같은 경기를 시작할 수 있게 한다.

최종 사용자 흐름은 다음과 같다.

```text
게임 실행
→ Epic 로그인 및 백엔드 인증
→ 게임 전용 고유 닉네임 등록·조회
→ 게임 시작 버튼 클릭
→ 사용자 4명을 하나의 매치로 배정
→ 호스트 1명이 EOS 세션과 리슨 서버 준비
→ 나머지 3명이 자동 참가
→ 같은 게임 맵에서 접속과 닉네임 확인
→ 경기 시작
```

## 3. 담당 범위

### 백엔드·인프라

- EOS 인증 증명 검증과 API 접근 제어
- PUID 기반 플레이어 식별
- 게임 전용 고유 닉네임 등록·조회
- 4인 중앙 매칭과 중복 배정 방지
- 매칭 요청의 취소·만료·재시도 처리
- 호스트 지정과 EOS 세션 정보 등록·전달
- 매치 상태와 장애 추적 정보 관리
- AWS 인프라의 코드화, 배포, 로그, 모니터링
- Unreal 클라이언트가 사용할 API 계약 관리

### 클라이언트팀과 함께 검증할 영역

- Epic 로그인 및 EOS Connect 연동
- 인증 토큰 전달과 갱신
- EOS 세션 생성·참가와 P2P 연결
- 리슨 서버 실행과 맵 이동
- 실제 4인 접속 확인 후 경기 시작
- 패키징된 Windows 빌드의 통합 테스트

### 담당 범위 밖

- 캐릭터 조작, 물리, 승패 판정
- Unreal Replication·RPC 구현
- 전적, 랭크, MMR
- 파티 매칭, 친구 초대
- 관전, 리플레이
- 경기 도중 호스트 마이그레이션
- 데디케이티드 서버

## 4. 확정된 기술 방향

| 영역 | 방향 |
|---|---|
| 게임 엔진 | Unreal Engine |
| 계정 로그인 | Epic Account Services(EAS) |
| 내부 사용자 식별 | EOS Product User ID(PUID) |
| 게임 연결 | EOS 세션 및 P2P |
| 게임 서버 | 플레이어 1명이 담당하는 리슨 서버 |
| 백엔드 | Amazon API Gateway + AWS Lambda |
| 데이터 저장소 | Amazon DynamoDB, 상세 설계 예정 |
| 운영 관측 | Amazon CloudWatch |
| 배포 대상 | Windows 실행 파일 직접 배포 |

클라이언트는 EOS와 AWS API를 각각 호출한다. Lambda는 매칭과 상태를 처리하며 게임 틱이나 물리 연산을 실행하지 않는다.

## 5. 핵심 설계 원칙

### 인증과 사용자 식별

- 요청 본문의 PUID를 신뢰하지 않는다.
- 검증된 EOS 인증 결과에서 요청자를 식별한다.
- 인증 토큰과 민감 정보는 로그에 남기지 않는다.
- 자체 비밀번호와 로그인 계정 DB는 만들지 않는다.

### 프로필과 닉네임

- 게임 화면에는 게임 전용 닉네임을 표시한다.
- 닉네임은 전체 사용자 범위에서 고유해야 한다.
- 정규화된 닉네임 점유와 프로필 생성을 원자적으로 처리한다.

### 매칭과 동시성

- 한 사용자를 둘 이상의 활성 매치에 배정하지 않는다.
- 4개의 티켓 선점과 매치 생성을 원자적으로 처리한다.
- 지연된 취소나 응답이 새 티켓을 변경하지 않도록 티켓 ID를 검증한다.
- 인덱스 조회 결과를 그대로 신뢰하지 않고 원본 항목의 상태와 유효시간을 다시 확인한다.
- API 중복 요청과 작업 재시도를 고려해 멱등성을 보장한다.

### 만료와 복구

- 애플리케이션의 유효기간 판단과 DynamoDB TTL 삭제를 구분한다.
- TTL을 정확한 시각에 실행되는 타이머로 사용하지 않는다.
- 경기 종료, 이탈, 실패 후 활성 상태를 해제해 다시 매칭할 수 있게 한다.
- 경기 시작 전 호스트 재선정은 상세 정책에 따라 제한적으로 처리한다.

### 관측과 운영

- 모든 요청을 `requestId`, `playerId`, `ticketId`, `matchId`로 추적할 수 있게 한다.
- 로그는 구조화하고 인증 정보와 민감 데이터를 제외한다.
- 매칭 시간, 세션 준비 시간, 실패율을 측정할 수 있게 한다.
- 개발 환경과 발표 환경의 설정을 분리한다.

## 6. 초기 도메인 뼈대

아래 항목은 상세 설계의 출발점이며 최종 스키마가 아니다.

### 데이터 영역

- `PlayerProfiles`: 프로필과 닉네임 점유
- `MatchmakingTickets`: 사용자의 현재 매칭 요청과 상태
- `Matches`: 배정된 사용자, 호스트, EOS 세션, 매치 상태

### API 영역

```http
GET    /me
POST   /me/nickname

POST   /matchmaking/tickets
GET    /matchmaking/tickets/current
DELETE /matchmaking/tickets/current

GET    /matches/{matchId}
POST   /matches/{matchId}/session
POST   /matches/{matchId}/joined
POST   /matches/{matchId}/started
```

### 매치 상태 예시

```text
FORMING → SESSION_READY → READY_TO_START → IN_GAME
```

실패, 취소, 만료, 호스트 재선정 상태와 전이 조건은 상세 설계에서 확정한다.

스프린트별 문서는 다음 구조를 기본으로 사용한다.

## 8. 공통 완료 기준

각 기능은 다음 항목을 충족해야 완료로 간주한다.

- [ ] 요구사항과 제외 범위가 문서화되어 있다.
- [ ] 정상 흐름과 주요 실패 흐름이 구현되어 있다.
- [ ] 권한 검사, 입력 검증, 중복 요청 처리가 확인되었다.
- [ ] 자동화 테스트 또는 재현 가능한 검증 절차가 있다.
- [ ] 로그에서 요청과 관련 리소스를 추적할 수 있다.
- [ ] 민감 정보가 응답이나 로그에 노출되지 않는다.
- [ ] 클라이언트 계약 변경이 공유되고 문서에 반영되었다.
- [ ] 배포 및 롤백 방법이 확인되었다.
- [ ] 남은 위험과 후속 작업이 기록되었다.

## 9. 단계별 큰 목표

| 단계 | 목표 |
|---|---|
| Sprint 1 | DB 상세 설계, AWS·EOS 개발 환경, API 기반 준비 |
| Sprint 2 | EOS 인증과 고유 닉네임 프로필 구현 |
| Sprint 3 | 동시성에 안전한 4인 중앙 매칭 구현 |
| Sprint 4 | 호스트 지정과 EOS 세션 연결 준비 |
| Sprint 5 | Unreal 통합, 배포, 실제 4인 경기 시작 검증 |

각 단계의 구체적인 작업과 완료 조건은 해당 스프린트 체크리스트에서 관리한다.
